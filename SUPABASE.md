# Supabase: база данных с готовым API (обход блокировок)

## Почему мы поменяли план

Первоначальный план был «Neon (база) + Render (сервер)». Проверка доступности с твоего
компьютера показала:

| Сервис | Результат |
|---|---|
| neon.tech | ❌ `403 Access Blocked in Your Region` — сервис блокирует доступ из твоего региона |
| render.com | ❌ соединение не устанавливается |
| railway.app | ❌ соединение не устанавливается |
| **supabase.com** | ✅ доступен |

Поэтому используем **Supabase**. Это PostgreSQL в облаке, который вдобавок сам генерирует
**REST API** для таблиц. Значит, отдельный хостинг для Node-сервера не нужен вообще:
приложение обращается к базе напрямую по HTTPS.

```
Телефон одногруппника
        │
        ▼
vk.com/app54822849  ──►  Хостинг ВКонтакте (статика: HTML, JS, CSS)
        │
        │  HTTPS-запросы к REST API
        ▼
Supabase: PostgreSQL + автоматический REST API
```

Наш Express-сервер при этом никуда не исчезает: он остаётся для локальной разработки и как
второй вариант бэкенда. Слой хранения в приложении умеет работать с тремя источниками, и выбор
происходит автоматически по настройкам окружения:

| Что настроено | Что использует приложение |
|---|---|
| `VITE_SUPABASE_URL` + ключ | Supabase (общие данные для всей группы) |
| `VITE_API_URL` | наш Express-сервер |
| ничего | localStorage (данные только в этом браузере) |

## Шаг 1. Создать проект в Supabase (3 минуты)

1. Открой https://supabase.com → **Start your project** → войди через GitHub или почту.
2. **New project**:
   - Name: `vk-group-app`
   - Database Password: сгенерируй и сохрани (для нашего способа он почти не нужен, но пусть будет)
   - Region: ближайший доступный (например, Frankfurt)
3. Дождись окончания создания (1–2 минуты).

## Шаг 2. Создать таблицы (2 минуты)

1. В левом меню проекта: **SQL Editor** → **New query**.
2. Открой файл [supabase/schema.sql](supabase/schema.sql), скопируй **всё** содержимое
   и вставь в редактор.
3. Нажми **Run** (Ctrl+Enter). Внизу должно появиться `Success. No rows returned`.

Что делает скрипт: создаёт 4 таблицы (`subjects`, `lessons`, `tasks`, `meta`), включает защиту
на уровне строк, добавляет политики доступа и заливает тестовые данные группы ИС-31.
Скрипт можно запускать повторно — дубликаты не появятся.

## Шаг 2.1. Обновление схемы №2: очно-заочный режим и материалы

Файл **`supabase/migrations/002-materials-and-lesson-modes.sql`** добавляет:

| Что добавляется | Зачем |
|---|---|
| `lessons.lesson_mode` — период обучения (`session` / `online`) | у очно-заочников занятия сессии идут по дням недели, а дистанционные — по датам |
| `lessons.lesson_date` — дата занятия | для вебинаров дистанционного периода |
| `tasks.attachment_path`, `attachment_name`, `attachment_link` | файл или ссылка, прикреплённые к заданию |
| таблица `materials` | учебные материалы по предметам (конспекты, методички, записи) |
| бакет `materials` в файловом хранилище | там физически лежат загруженные файлы |

Применяется так же: **SQL Editor → New query → вставить весь файл → Run**.
Скрипт безопасно запускать повторно, существующие данные он не удаляет.

> Порядок важен: сначала схема `schema.sql`, потом это обновление.

## Шаг 3. Прислать мне два значения

> В новой панели Supabase ключи называются иначе, чем в старых статьях. Тебе нужен
> **Publishable key** — на странице **Project Settings → API Keys** он подписан
> «This key is safe to use in a browser». Именно он и есть публичный ключ для фронтенда.

| Что нужно | Где взять | Как выглядит | Секрет? |
|---|---|---|---|
| **Project URL** | **Project Settings → Data API** (строка «Project URL»). Либо из адресной строки браузера: в адресе есть `/project/<код>`, и адрес API — `https://<код>.supabase.co` | `https://abcdefgh.supabase.co` | нет |
| **Publishable key** | **Project Settings → API Keys** → раздел «Publishable key» | `sb_publishable_Lmobp...` (раньше выглядел как `eyJhbGciOi...`) | **нет, этот ключ создан для браузера** |

Приложение понимает **оба** формата ключа: и новый `sb_publishable_...`, и старый `anon` (JWT,
начинается с `eyJ`). Разница только в заголовках запроса, и это уже учтено в коде.

> ⚠️ **Secret key** (`sb_secret_...`, раздел «Secret keys») — настоящий секрет, он даёт полный
> доступ к базе в обход политик. Не пересылай его никому, включая меня. Работать с ним
> в мини-приложении нельзя ни в каком виде: код фронтенда видит любой пользователь.

## Шаг 4. Что сделаю я

1. Пропишу адрес и ключ в настройки приложения.
2. Проверю REST API Supabase реальными запросами с твоего компьютера (создание, чтение,
   изменение, удаление) — до того, как ты это увидишь.
3. Передеплою мини-приложение (деплой у меня уже полностью автоматический).
4. Проверю, что в приложении появилось «Режим данных: общий сервер».

## Что честно сказать на защите

- **Почему Supabase.** Это управляемый PostgreSQL с автоматически генерируемым REST API
  (технология PostgREST). Мы получили облачную базу без необходимости поднимать и обслуживать
  свой сервер. Для учебного проекта это дало бесплатное решение, доступное из нашего региона.
- **Что с нашим Express-сервером.** Он остался в проекте и работает: слой хранения в приложении
  поддерживает три источника данных (Supabase, собственный сервер, локальное хранилище) и
  переключается настройками. Ни один экран интерфейса при этом не менялся — это и есть польза
  слоя абстракции.
- **Про безопасность.** В учебном проекте политики доступа разрешают анонимные чтение и запись,
  потому что в мини-приложении нет логина. В боевом варианте нужны Supabase Auth, политики
  «каждый видит только свою группу» и серверная проверка прав.

## Ограничения бесплатного тарифа

| Ограничение | Что это значит |
|---|---|
| 500 МБ базы, 2 проекта | для учебной группы более чем достаточно |
| Проект «засыпает» после недели без запросов | восстанавливается кнопкой Restore в панели Supabase; во время защиты просто открой приложение заранее |
| Логи запросов хранятся ограниченное время | для отладки хватает |
